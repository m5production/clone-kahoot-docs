# 13. Вопросы с выбором ответа

Спецификация функции «вопросы с выбором из 2–4 вариантов» — пункт 18 бэклога P3
([документ 8](08-gaps-and-backlog.md)), функция после версии 1.0. Формат
оригинального Kahoot: игрок видит цветные кнопки-варианты и выбирает один, вместо
ввода текста.

## Решения

| ID | Решение |
|---|---|
| D-10 | У вопроса есть тип: `open` (текстовый ответ, как сейчас) или `choice` (выбор из вариантов). Тип задаёт ведущий в конструкторе, по умолчанию у существующих и новых вопросов — `open`. |
| D-11 | Варианты — отдельная сущность `QuestionOption` с явным порядком и отметкой «верный». В вопросе `choice` 2–4 варианта и ровно один верный; игрок выбирает один вариант, ответ верен, если выбран помеченный вариант. |
| D-12 | Вопрос не может одновременно иметь принимаемые ответы и варианты. При смене типа в конструкторе набор неактивного типа удаляется (с подтверждением в UI, если он не пуст). |
| D-13 | Варианты показываются всем в одинаковом порядке, заданном ведущим (нет перемешивания). Правильность вариантов не уходит клиентам до `ANSWERS_REVEALED` — в `SESSION_STATE` варианты приходят без `isCorrect`. |
| D-14 | Очки — по той же формуле BR-70 (1000→500 за скорость) для верного выбора, иначе 0. `SessionAnswer.text` хранит текст выбранного варианта. |
| D-15 | Квиз может смешивать вопросы обоих типов. Проверка готовности BR-49 расширяется: `open` — текст и ≥1 принимаемый ответ; `choice` — текст и 2–4 варианта, из них ровно один верный. |

## Новые требования

### Пользовательские истории

- **US-35. Создать вопрос с вариантами.** Как ведущий, я хочу выбрать тип вопроса «выбор из вариантов», задать 2–4 варианта ответа и отметить один верный, чтобы игроки отвечали кнопками.
- **US-36. Ответить кнопкой.** Как игрок, я хочу видеть варианты ответа цветными кнопками и выбирать один, чтобы отвечать быстрее и без опечаток.
- **US-37. Видеть разбор по вариантам.** Как ведущий, я хочу после вопроса видеть, какой вариант верный и кто что выбрал, а потом — тот же разбор в отчёте игры.

### Функциональные требования

| ID | Требование | История |
|---|---|---|
| FR-98 | В конструкторе у вопроса есть переключатель типа «текстовый ответ» / «выбор из вариантов» (US-35). | US-35 |
| FR-99 | Для `choice` форма показывает список вариантов (2–4) с радиокнопкой «верный» — выбрать можно только один; добавление и удаление вариантов в пределах лимита (US-35). | US-35 |
| FR-100 | Сохранение `choice`-вопроса отклоняется с ошибкой у поля, если вариантов меньше 2 или не отмечен верный; дубли вариантов подсвечиваются (BR-86). | US-35 |
| FR-101 | Во время вопроса `choice` игрок видит сетку кнопок-вариантов (2 колонки на широком экране, цвет по индексу: красный, синий, жёлтый, зелёный); нажатие отправляет выбор и блокирует кнопки (US-36). | US-36 |
| FR-102 | После показа ответов игрок и ведущий видят варианты с подсветкой верных и своим/чужим выбором; у ведущего — список «игрок → выбранный вариант» (US-37). | US-37 |
| FR-103 | Отчёт игры показывает для `choice`-вопросов варианты с отметкой верных и выбор каждого игрока (US-37, FR-81). | US-37 |

### Бизнес-правила

| ID | Правило |
|---|---|
| BR-86 | У `choice`-вопроса 2–4 варианта, каждый ≤ 100 символов, без дублей после нормализации (BR-64), ровно один верный. Вопрос одного типа не хранит данных другого типа (D-12). |
| BR-87 | Игрок выбирает ровно один вариант; действуют BR-62 (не после закрытия) и BR-63 (первый ответ считается). Ответ верен, если выбранный вариант помечен верным (D-11). |
| BR-88 | Верность вариантов скрыта от клиентов до `ANSWERS_REVEALED` (продолжение BR-66): `SESSION_STATE` и состояние до показа ответов не содержат `isCorrect`. |

## Доменная модель и миграция

```prisma
model Question {
  // ... без изменений, плюс:
  type    String           @default("open") @db.VarChar(16) // 'open' | 'choice'
  options QuestionOption[]
  // answers AcceptedAnswer[] — остаётся, используется только при type='open'
}

model QuestionOption {
  id         String   @id @default(cuid())
  questionId String
  question   Question @relation(fields: [questionId], references: [id], onDelete: Cascade)
  order      Int
  text       String   @db.VarChar(100)
  isCorrect  Boolean  @default(false)

  @@unique([questionId, order])
  @@index([questionId])
}

model SessionQuestion {
  // ... плюс:
  type    String  @default("open") @db.VarChar(16)
  options Json?   // снапшот для choice: [{text, isCorrect}]
}
```

- Миграция: `Question.type` с `CHECK IN ('open','choice')`, таблица
  `QuestionOption`, `SessionQuestion.type` + `options`. `SessionAnswer.text`
  достаточно (`VarChar(100)` хранит текст выбранного варианта).
- Инвариант D-12 проверяется в сервисах: `assertValidOptions` (аналог
  `assertValidAnswerTexts` в `accepted-answers.util.ts`) — 2–4 штуки, ровно один верный,
  без дублей; при смене `type` чужой набор удаляется в той же транзакции.

## REST API

| Метод | Путь | Изменение |
|---|---|---|
| `PUT` | `/questions/:id` | `UpdateQuestionDto` += `type?: 'open' \| 'choice'`; смена типа удаляет набор другого типа (D-12) |
| `GET` | `/questions?gameId=` | элемент списка += `type`, `optionsCount` (для готовности BR-49) |
| `GET` | `/options?questionId=` | новый модуль `options`: список вариантов владельцу |
| `PUT` | `/options?questionId=` | транзакционная замена `[{text, isCorrect}]`, валидация BR-86 — зеркало `PUT /accepted-answers` |

## WebSocket-протокол

Изменения к [протоколу](../backend/docs/websocket-protocol.md):

- `SESSION_STATE.question` += `type: 'open' | 'choice'` и для `choice` —
  `options: [{id, text}]` **без** `isCorrect` (BR-88); `id` — id `QuestionOption`.
- `ANSWER_QUESTION` payload: `open` — `{questionId, answer}` (как сейчас);
  `choice` — `{questionId, optionId}`. Неизвестный `optionId` → `FAULT BAD_REQUEST`.
- `ANSWER_ACCEPTED`: `choice` — `{questionId, optionId, text}`; эхо при
  переподключении (BR-58) отправляет тот же формат.
- `ANSWERS_REVEALED`: `choice` — `correctOptionId: id`, в `answers[]` у игрока
  `optionId` и `text` выбранного варианта; `open` — как сейчас (`acceptedAnswers`).

Снапшот вопроса в комнате (`QuestionSnapshot`) += `type`, `options: {id, text,
isCorrect}[]`; проверка ответа: `open` — по `acceptedNormalized`, `choice` — по
`isCorrect` выбранного `optionId`. Автозакрытие «все ответили» и таймер не
меняются. `history.startRecord` пишет `type` и `options`-снапшот в
`SessionQuestion`.

## Фронтенд

- `entities/question`: `Question.type`, `optionsCount`; `isQuestionReady`
  учитывает тип (BR-49). Новый слайс `entities/answer-option` — зеркало
  `entities/accepted-answer` (types, api, queries).
- `features/question/edit-question`: переключатель типа (segmented control) над
  списком ответов; для `choice` — `useFieldArray` вариантов с радиокнопкой «верный»,
  кнопки «добавить вариант» (скрыта на 4) и удаления (скрыта на 2); валидация
  BR-86 и подтверждение смены типа при непустом другом наборе (D-12).
- `features/active-game/submit-answer`: рядом с текстовой формой — компонент
  кнопок-вариантов; выбор по `session.question.type`. Тест-ids: `answer-option-0..3`
  (см. `.devin/rules/test-ids.md`).
- `pages/session`: на экране `choice`-вопроса варианты видны ведущему и игроку;
  после `ANSWERS_REVEALED` — подсветка верных и выбранных.
- `pages/session-report`: разбор `choice`-вопроса списком вариантов с отметками.

## Этапы

Порядок соблюдать; внутри этапа бэкенд и фронтенд можно вести параллельными PR,
сливать — вместе или бэкенд первым. Каждый этап оставляет приложение рабочим.

### Этап 1. Бэкенд: модель и REST

- Миграция: `Question.type`, `QuestionOption`, `SessionQuestion.type/options`.
- Модуль `options` (controller/service/dto), `UpdateQuestionDto.type` с очисткой
  чужого набора, `type`/`optionsCount` в списке вопросов, готовность к запуску
  (D-15) в `createSession`.
- Тесты: node:test на `assertValidOptions` и на валидацию `type` в DTO.
- Результат: данные и API есть, протокол не изменён — игра работает как раньше.

### Этап 2. Бэкенд: игра и протокол

- `QuestionSnapshot` с вариантами, `ANSWER_QUESTION` по `optionId`,
  `ANSWERS_REVEALED` с `correctOptionId`, эхо `ANSWER_ACCEPTED` при reconnect,
  запись `type`/`options` в историю.
- Тесты: node:test на выбор верного/неверного варианта и очки BR-70.
- Обновить `backend/docs/websocket-protocol.md` и `api.md` в том же PR.

### Этап 3. Фронтенд: конструктор (параллельно этапу 2)

- `entities/answer-option`, тип в `Question`, `isQuestionReady` по типу.
- Форма `choice`: список вариантов, радиокнопка «верный», лимиты 2–4, переключатель
  типа с подтверждением.
- Компонентные тесты браузерного режима на форму.

### Этап 4. Фронтенд: игра и отчёт

- Кнопки-варианты у игрока (цвет по индексу, блокировка после выбора, состояния
  «отвечено»/«время вышло» — как у текстовой формы).
- Показ вариантов у ведущего; разбор после `ANSWERS_REVEALED` (верные, выбор
  каждого игрока); рендер вариантов в отчёте игры.
- Типы сообщений в `entities/active-game`, компонентные тесты.

### Этап 5. E2E и документы

- Playwright-сценарий: ведущий собирает квиз с `choice`-вопросом → игра →
  игрок отвечает кнопкой → разбор → победители → отчёт.
- Документы: пункт 18 бэклога — закрыт (документ 8); документы 3–6 — новые
  FR-98–FR-103, BR-86–BR-88, US-35–US-37, `QuestionOption` в доменной модели,
  протокол в документе 6; документ 1 — убрать «выбор из вариантов» из «не входит».

```
Этап 1 (модель+REST) ──┬──► Этап 2 (игра+протокол) ──┐
                       └──► Этап 3 (конструктор) ────┤
                                                    └──► Этап 4 (игра+отчёт) ──► Этап 5 (e2e+доки)
```

## Критерии приёмки

- Ведущий создаёт `choice`-вопрос с 2–4 вариантами и ровно одним верным; квиз с неготовым
  `choice`-вопросом не запускается.
- Игрок отвечает одной кнопкой; повторный выбор → `CONFLICT`; после таймера → `BAD_REQUEST`.
- До показа ответов ни в одном сообщении нет `isCorrect` вариантов.
- Очки за верный выбор — по BR-70; история и отчёт показывают варианты и выбор игроков.
- Смешанный квиз (`open` + `choice`) проходит целиком; `open`-вопросы не изменились.
- `yarn typecheck`/`lint`/`test` бэкенда и `bun run check` + `test:e2e` фронтенда зелёные.
