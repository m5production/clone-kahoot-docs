# 10. План реализации версии 1.0

Пошаговый план доведения продукта до состояния из [целевых требований](09-target-requirements.md). Каждый этап — самостоятельно сливаемый объём работ (один или несколько PR), после которого приложение остаётся рабочим. Нумерация этапов отражает зависимости, не приоритет в вакууме.

Ссылки на требования: US/FR/BR — документы 2–4 и 9, GAP — [бэклог](08-gaps-and-backlog.md), NFR — документ 7 и раздел 9.9.

## Текущее состояние (точка старта)

Изменения, которые план считает уже выполненными:

- Бэкенд — NestJS + Prisma + PostgreSQL; сессии — Bearer-токен в localStorage, хеш токена в `Session` (D-9); WS-аутентификация одноразовым билетом (`POST /api/auth/ws-ticket`).
- Живые игры — комнаты в памяти `ActiveGameService` (`Map<gameId, Room>`), несколько комнат одновременно, рассылка только участникам комнаты.
- Уже закрыто: GAP-1…GAP-5, GAP-8, GAP-14; каскадные удаления в БД; поле `Question.order`; первый ответ засчитывается; `GAME_DATA` не выдаёт правильности до показа; ошибки `{code,message,requestId}` и `FAULT`; rate-limit на вход/регистрацию; unit + e2e (19 Playwright) тесты; CI бэкенда.
- Ещё нет: названий и `updatedAt` у квизов, `timeLimitSec` у вопросов, лобби, ссылок-приглашений, таймера, очков за скорость, истории игр, переподключения ведущего, раздельных экранов входа/регистрации.

Актуальный WS-протокол — `backend/docs/websocket-protocol.md`; целевой — раздел 9.8.

## Правила исполнения

1. **Порядок этапов соблюдать.** Внутри этапа бэкенд и фронтенд можно делать параллельными PR, но сливать — вместе или бэкенд первым.
2. **Проверки перед слиянием.** Бэкенд: `yarn lint && yarn typecheck && yarn test && yarn build`. Фронтенд: `bun run check`, плюс `bun run test:e2e` при изменении пользовательских сценариев.
3. **Миграции только через `npx prisma migrate dev`** (см. `backend/AGENTS.md`); существующую БД не сбрасывать без явного подтверждения. Схему и контракты менять миграцией и обновлением `backend/docs/database.md`, `api.md`, `websocket-protocol.md` в том же PR.
4. **Статусы в документах.** По завершении этапа обновить статусы соответствующих FR в документе 3, закрытых GAP в документе 8 и отметить реализованные пункты в документе 9 — в том же PR (по README).
5. **Новые элементы интерфейса** получают `data-testid` по правилам `frontend/.devin/rules/test-ids.md`; каждый новый пользовательский сценарий — e2e-тест.
6. **ID требований** указывать в коммитах и описаниях PR.

## Этап 1. Вход и аккаунт: гостевые экраны и раздельная авторизация

Требования: D-7, US-31, US-32, FR-84–FR-87, BR-40–BR-42, BR-83–BR-85; закрывает смену FR-1, FR-2, FR-5.

### Бэкенд

- Ужесточить `CredentialsDto` (`auth.controller.ts`): `name` — trim, 3–20 символов; `password` — 8–128 (BR-40, BR-41).
- Уникальность никнейма без учёта регистра (BR-40): уникальный индекс `lower(name)` в миграции; хранить имя как введено, конфликт → 409.
- `SESSION_TTL_SECONDS`: дефолт 604800 → 2592000 (30 дней, BR-42); задать в `.env.example`.
- Эндпоинты не меняются: `POST /users` (409 на занятое имя), `POST /users/auth` (401 «Invalid name or password» — уже одинакова для неизвестного имени и неверного пароля, BR-84), `POST /users/logout`, `GET /users/me`.
- Unit-тесты сервиса на новые границы валидации и регистронезависимый конфликт имён.

Осторожно: тестовые пароли в e2e-фикстурах фронтенда короче 8 символов (`secret`, `right`, `wrong`) — обновить фикстуры и сид-пользователей, иначе e2e упадёт.

### Фронтенд

- Маршруты: `/` → страница приветствия, `/login`, `/register` — гостевые; остальные под `RequireAuth` с редиректом на `/` (FR-84, BR-85).
- Страница приветствия: описание продукта, кнопки «Войти» и «Зарегистрироваться» → `/login`, `/register` (FR-84).
- Разнести `features/session/login` на вход (только `authenticateUser`) и регистрацию (`createUser`, затем вход — токен уже приходит в ответе). Удалить fallback `loginOrRegister` (FR-85, FR-86).
- Перекрёстные ссылки «Уже есть аккаунт?» / «Нет аккаунта?» между `/login` и `/register`; `GuestOnly`-обёртка: вошедший на гостевой странице → `/home` (FR-87); восстановление сессии перенести из `login.model` в общее место (сейчас логика в `useLogin`).
- Ошибки: неверные креды на входе и занятое имя на регистрации — тост с текстом сервера; сетевая ошибка — общий `notifyApiError`.

### Тесты и приёмка

- Обновить `login.service.unit.spec`, `login.ui.browser.spec` под два сервиса/формы; новые component-тесты регистрации и welcome-страницы; переписать `e2e/auth.e2e.ts`: регистрация нового пользователя через `/register`, ошибка входа с несуществующими кредами (без создания аккаунта), ошибка занятого имени, редиректы гостя на welcome и вошедшего на `/home`.
- Критерий: невозможно создать аккаунт со страницы входа; гость видит welcome на любой странице.

## Этап 2. Квизы: название, удаление, порядок, валидация

Требования: US-17–US-20 (частично), FR-50–FR-56, BR-44–BR-47, BR-49, изменение BR-11; закрывает GAP-6, GAP-10, GAP-12 (UI), GAP-13.

### Бэкенд

- Миграция: `Game.title VarChar(80)` (обязательное; для существующих строк — бэкфилл «Quiz #<порядковый>»), `Game.updatedAt` (`@updatedAt`).
- `updatedAt` трогать и при изменениях вопросов/ответов квиза (BR-45: сортировка списка по изменению). Список `GET /games` → `{id,title,questionCount,updatedAt}` по `updatedAt desc` (FR-51).
- Валидация на сервере (BR-44, BR-46, BR-47, NFR-S10): `title` trim 1–80; `Question.text` ≤300 — сузить `VarChar(500)` → `VarChar(300)`; `AcceptedAnswer.text` ≤100 — `VarChar(200)` → `VarChar(100)`; ответов 1–10 на вопрос; ответы, дублирующиеся после нормализации (trim + lowercase), → 400.
- Реордеринг: `PATCH /api/games/:id/questions/reorder {questionIds: string[]}` — массив обязан быть перестановкой текущих id; перенумерация `order` в одной транзакции (FR-54).
- `POST /games` принимает `title`; `PATCH /games/:id` — переименование (FR-50). Ошибки — единый `{code,message,requestId}`.

### Фронтенд

- Создание квиза — диалог/поле с названием; переименование в конструкторе; список квизов показывает название, число вопросов, дату изменения (FR-50, FR-51).
- Удаление квиза из интерфейса с подтверждением (FR-52, US-18). Блокировка удаления/правки во время идущего сеанса — с этапа 4 (BR-54), здесь оговорить в коде TODO.
- Перестановка вопросов в списке: кнопки «вверх»/«вниз» (простой путь) или dnd (FR-54); вызывает reorder-endpoint, optimistic + откат.
- Конструктор: запуск недоступен, пока квиз не готов (FR-55, BR-49) — подсветка неготовых вопросов; ошибки лимитов у конкретных полей (FR-56); селект времени на вопрос — с этапа 4b (FR-53), можно заложить disabled-контрол заранее.

### Тесты и приёмка

- Unit: нормализация-дедупликация ответов, reorder-валидация. E2e: создание с названием, переименование, удаление каскадом, перестановка, блокировка запуска неготового квиза.

## Этап 3. Нормализация ответов

Требования: D-1, BR-64; закрывает GAP-7. Маленький этап, но отдельным PR — меняет правила игры.

### Бэкенд

- `normalizeAnswer(text)` = `trim().toLowerCase()` в общем util (используется и при валидации принимаемых ответов этапа 2, и в игре).
- `ActiveGameService`: множество принимаемых ответов строить по нормализованным строкам; ответ игрока сравнивать после нормализации. Пустой после trim — отклонять (уже есть непустая проверка — привести к BR-63).
- Unit-тесты: `paris`, ` Paris `, `PARIS` ≡ `Paris`; `ё`/`е` и внутренние пробелы НЕ сворачиваются (явные кейсы из BR-64).

## Этап 4a. Игровой сеанс: лобби, ссылка-приглашение, строгий порядок

Требования: D-2, D-8, US-21–US-22, US-26–US-28, FR-60–FR-64, FR-66–FR-68, FR-71–FR-76 (без таймера), BR-50–BR-60, BR-65–BR-66; закрывает GAP-11.

Самый объёмный этап: меняет модель комнаты и протокол. Целевой протокол — раздел 9.8.

### Бэкенд: модель сеанса

- Комнаты ключировать по `sessionId` (cuid), а не `gameId`. `Room`: `{sessionId, gameId, quizTitle, hostId, hostSocket, state, questionIndex, questionsSnapshot, players, sockets, hostGraceTimer, questionTimer?}`.
- Снапшот вопросов с принимаемыми ответами в память при старте (BR-54). Пока `sessionId` живёт только в памяти — строка в БД появится на этапе 5.
- REST для жизненного цикла вне сокета:
  - `POST /api/games/:id/sessions` — только владелец; 409 если по квизу уже идёт сеанс или ведущий ведёт другой — ответ содержит `sessionId` существующего для возврата (BR-51, FR-61); ответ `{sessionId, joinPath}`.
  - `GET /api/sessions/:id` — публичная сводка `{state, quizTitle, hostName}` для страницы `/join/:id`; завершённый/несуществующий → 404/410 (FR-73).
- Блокировка квиза: `ActiveGameService.isRunning(gameId)`; games/questions/accepted-answers при идущем сеансе → 409 (BR-54).

### Бэкенд: протокол (по 9.8)

| Было | Стало |
|---|---|
| `START_GAME {gameId}` | REST `POST /games/:id/sessions`; затем `START_GAME` переводит лобби → первый вопрос |
| `PLAYER_CONNECTED {gameId}` | `JOIN_SESSION {sessionId}` — вход и переподключение ведущего и игрока |
| `CHANGE_QUESTION {questionId}` | `NEXT_QUESTION` — только следующий по порядку (BR-60) |
| `END_GAME` | `END_SESSION` — с подтверждением на клиенте, причина в `SESSION_ENDED` |
| `GAME_DATA` | `SESSION_STATE` — состояние, название квиза, игроки (ник, цвет, в сети, ответил), текущий вопрос без ответов, номер из общего числа |
| `SHOW_ANSWERS` | `ANSWERS_REVEALED` — принимаемые ответы + ответ каждого игрока с верностью; только из состояния «вопрос закрыт» (BR-66) |
| `SHOW_WINNERS` | `WINNERS` — после последнего вопроса |

Новые сообщения: `CLOSE_QUESTION` (досрочно, BR-61), `ANSWER_ACCEPTED` ответившему, `QUESTION_CLOSED` всем (автозакрытие, когда ответили все в сети — BR-61), `SESSION_ENDED {reason: finished|host_ended|host_timeout}`.
Уточнение к 9.8 (внести в док): `SESSION_STATE` дополнить `hostConnected`, чтобы игроки видели ушедшего ведущего.

### Бэкенд: отключения

- Игрок: текущее поведение сохранить — `connected:false`, ответы хранятся до конца (BR-58). Подключение разрешено в любом состоянии, кроме `finished` (BR-57); опоздавший получает только текущий вопрос, пропущенные — 0 (D-2).
- Ведущий: отключение больше НЕ завершает комнату (BR-59). Комната живёт, `hostConnected:false` в `SESSION_STATE`; `hostGraceTimer` 5 мин (конфиг `HOST_GRACE_SECONDS`); переподключение по `JOIN_SESSION` с той же ролью до истечения → продолжение; истёк → `SESSION_ENDED {reason:host_timeout}`, комната удаляется (статус «прервана» — запись с этапа 5). Снять текущее `endRoom` по disconnect ведущего.

### Фронтенд

- Маршрут `/join/:sessionId` под `RequireAuth`: `GET /api/sessions/:id` → сводка («Квиз X, ведущий Y») → ws `JOIN_SESSION`. Не вошёл → welcome → login/register → возврат на ту же ссылку (return-url, US-22, FR-72). Ошибки — экран «ссылка недействительна / игра закончилась» (FR-73).
- Лобби ведущего: ссылка с кнопкой копирования, QR-код (добавить зависимость `qrcode`, ≥7 дней в npm), список игроков со статусами, кнопка «Начать игру» (FR-62, FR-63, US-21).
- Лобби игрока: название квиза, свой ник, список игроков (FR-74).
- Ведущий в игре: «Следующий вопрос», «Закрыть вопрос», «Показать ответы», «Показать победителей», «Завершить игру» с подтверждением; счётчик «ответили N из M»; индикатор `hostConnected` у игроков (FR-64–FR-70).
- Показ ответов: принимаемые ответы + ответ каждого игрока с верностью — даже если никто не ответил верно (FR-67); игрок видит свой текст и свою отметку (FR-76, FR-78).
- Игрок: после отправки — «Ответ принят», поле заблокировано (FR-76); `SESSION_ENDED` → экран «Игра завершена» / таблица победителей + кнопка домой (FR-79).
- Переподключение: ws-reconnect с backoff до 5 мин, повторный `JOIN_SESSION` (FR-77, NFR-R5) — общий механизм для ведущего и игрока.

### Тесты и приёмка

- Unit: переходы состояний, отклонение команд не в том состоянии, `host_timeout`, изоляция комнат. E2e: запуск → лобби → вход по ссылке → полная игра → победители; уход и возврат ведущего <5 мин; досрочное завершение; опоздавший игрок. Сквозной критерий 3 из 9.10 — прогон на двух параллельных сеансах.

## Этап 4b. Таймер на вопрос и очки за скорость

Требования: US-20, US-23, US-24, FR-53, FR-65, FR-75, BR-48, BR-61–BR-62, BR-70–BR-73, NFR-P6; закрывает GAP-15 и P3-19.

### Бэкенд

- Миграция: `Question.timeLimitSec SmallInt` default 20 + `CHECK IN (10,20,30,60,90,120)` (BR-48); то же в снапшоте сеанса и (этап 5) `SessionQuestion`.
- Серверный таймер: при открытии вопроса `questionStartedAt`, `questionEndsAt`; `setTimeout` → автозакрытие; закрытие также при «ответили все в сети» и `CLOSE_QUESTION` (BR-61).
- Ответ: `responseTimeMs = receivedAt − questionStartedAt`; позже `questionEndsAt` — отклонить (BR-62).
- Очки (BR-70–71): верный `round(1000 × (1 − t/(2×timeLimit)))`, иначе 0; `points` и `responseTimeMs` в записи ответа.
- Рейтинг (BR-72–73): score desc, затем суммарный `correctTimeMs` asc; делёж мест при полном равенстве; `WINNERS`/`SESSION_STATE`-standings `{place, name, score, correctCount}`.
- Синхронизация таймера: `SESSION_STATE` несёт `questionEndsAt` и `serverNow` (NFR-P6).

### Фронтенд

- Конструктор: селект времени 10/20/30/60/90/120, дефолт 20 (FR-53).
- Таймер обратного отсчёта у ведущего и игрока: `remaining = questionEndsAt − (Date.now() + offset)`, `offset = serverNow − Date.now()`; блокировка поля по нулю и по `QUESTION_CLOSED` (FR-65, FR-75).
- При показе ответов — очки за вопрос у каждого ответа; в таблице победителей — место, очки, число верных, топ-3 выделены (BR-73, FR-78).

### Тесты и приёмка

- Unit: формула BR-70 на границах (t=0 → 1000, t=T → 500), отбраковка позднего ответа, тай-брейки BR-72. E2e: истечение времени закрывает вопрос у всех одновременно; очки и места в таблице совпадают с расчётом (критерий 4 из 9.10).

## Этап 5. История игр

Требования: D-5, US-29, US-30, FR-80–FR-83, BR-80–BR-82, NFR-R6, NFR-R7; закрывает GAP-17. Зависит от 4a (модель сеанса) и 4b (очки в данных).

### Бэкенд

- Миграция по ER-диаграмме 9.7: `GameSession` (`quizId` SetNull, `quizTitle` копией, `status running|finished|aborted`, `startedAt`, `endedAt`), `SessionQuestion` (полный снапшот + `acceptedAnswers` JSON), `SessionPlayer`, `SessionAnswer`.
- Запись: строка сеанса и снапшот вопросов — при старте; `SessionAnswer`/`SessionPlayer` — при закрытии каждого вопроса (NFR-R6); статус и `endedAt` — при завершении/прерывании.
- При старте процесса: все `status='running'` → `'aborted'` (NFR-R7).
- API: `GET /api/sessions` — своя история, новые сверху (дата, название, статус, число игроков, победитель — FR-80); `GET /api/sessions/:id/report` — ведущему: таблица + ответы по вопросам (FR-81); `DELETE /api/sessions/:id` — только ведущий (FR-82, BR-82). Доступ — только автор сеанса (BR-81). Увязать с `GET /api/sessions/:id` из 4a (публичная сводка живого сеанса ≠ отчёт).

### Фронтенд

- Страница «История игр» из главной и из карточки квиза (FR-80, FR-83); страница отчёта с таблицей и разбором по вопросам (FR-81); удаление записи с подтверждением (FR-82).

### Тесты и приёмка

- E2e: игра до конца → запись в истории с совпадающими очками; прерванная игра → статус «прервана»; удаление квиза не трогает историю; чужая история недоступна.

## Этап 6. Качество и эксплуатация

Параллельно с этапами 4–5 или после них.

- Rate-limit на WS-команды (не только на HTTP-вход) — незакрытый пункт чеклиста рефакторинга.
- Структурированные логи с `requestId` (без секретов и токенов).
- CI фронтенда (NFR-O4): GitHub Actions — install, Biome, `lint:circular`, `tsc -b`, Vitest; e2e — с сервисом PostgreSQL, как в CI бэкенда.
- NFR-O4: unit-тесты нормализации/очков/ранжирования (часть попадёт в этапы 3–4b), сквозной тест «игра → история».
- NFR-U5: вёрстка экрана игрока от 360 px (вопрос, таймер, поле ответа без прокрутки); NFR-U6 — проверка понятных текстов ошибок.
- NFR-P5: нагрузочная проверка 20 сеансов × 50 игроков (скрипт/ws-клиенты, без полноценного k6 — фиксация результатов в `backend/docs`).
- Эксплуатация Amvera: проверка health-check, секретов, бэкапов PostgreSQL — открытые пункты чеклиста бэкенда.
- Синхронизация документов 1–8 с новым кодом (ссылки на NestJS-модули и FSD-слои вместо старых путей Express/`src/pages`) и обновление статусов — по мере закрытия этапов.

- 4b требует `timeLimitSec` в снапшоте сеанса — поэтому после 4a; данные очков из 4b нужны истории — поэтому 5 после 4b.
- `POST /games/:id/sessions` из 4a — точка, к которой привязывается ссылка; история переиспользует `sessionId` как id записи.
